# Releasing

Work lands on `development`. `production` is what's live: Railway deploys it, and it moves only when a release is cut. Every release is tagged `vX.Y.Z`, and the version is kept in sync across `backend/pyproject.toml`, `backend/uv.lock`, `frontend/package.json`, and `frontend/package-lock.json`. `GET /api/v1/health` reports the version that's running.

## Cutting a release

From the repo root, on an up-to-date `development` with a clean working tree:

```bash
./release.sh --dry-run   # preview: checks run, nothing changes
./release.sh
```

The script:

1. Checks that you're on `development`, the tree is clean, `development` isn't behind `origin/development`, and `origin/production` has no commits that are missing from `development`.
2. Reads the current version from the latest `v*` tag, lists the commits since then, and asks for **major**, **minor**, or **patch**. It suggests a bump from the commit types: `!` or `BREAKING CHANGE` → major, `feat` → minor, anything else → patch. The first release can instead tag the current version as it is.
3. Runs the pre-commit hooks, both test suites, and the frontend production build. Skip them with `--skip-checks` only if you just ran them yourself.
4. Bumps the version, adds the new commits to `CHANGELOG.md` (generated by commitizen), commits `chore(release): vX.Y.Z`, and creates the annotated tag.
5. Fast-forwards `production` to the tag and pushes `development`, `production`, and the tag in one atomic push.

After the deploy, confirm that `/api/v1/health` returns the new version.

## Choosing the bump

While the version is `0.x`, the app is still pre-1.0:

- **patch**: bug fixes, copy changes, and rule or fee data corrections
- **minor**: new features, new permit coverage, and API changes (breaking ones included)
- **major**: reserve `1.0.0` for when the app is ready to call stable

## Rolling back

Redeploying a previous deployment from the Railway dashboard is the fastest fix. To make the branch match, point `production` back at the last good tag:

```bash
git push --force-with-lease origin v0.1.0^{commit}:refs/heads/production
```

Then fix the problem on `development` and release a patch. `release.sh` fast-forwards `production` again from there.

## Hotfixes

Land the fix on `development` and release a patch. If `development` has unreleased work that can't ship yet, branch off the production tag, cherry-pick the fix, tag the new patch version on that branch, and push it to `production`. Then merge that branch back into `development`, because `release.sh` refuses to run while `production` has commits that aren't on `development`.
